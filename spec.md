## Architecture

- **Acquisition** (`internal/acquisition`) — Modbus config is split into `connection` (the physical link — protocol/interface-or-ip+port/baud/parity/timeout/retry/`next_device_delay_ms`, `internal/connection`) and `device` (a slave ID + its data points, referencing one `connection_id`, `internal/device`) — several devices can share one physical RTU bus (real multi-drop). Polls one goroutine **per enabled connection**, not per device: `Poller.runConnection` owns a single `modbus.Client` for the connection's lifetime and calls `SetUnitID` before each sibling device's own reads, serialized by construction. Devices are scanned continuously, round-robin, paced only by `next_device_delay_ms` between devices; each device's datapoints are batched into as few Modbus block reads as possible (`internal/acquisition/blockplan.go`) instead of one request per datapoint.
- **Queue** (`internal/queue`) — persists every reading to SQLite (WAL) as `data_queue` with an atomic per-gateway `sequence_id`. Capacity is bounded two independent ways, both evicting oldest non-critical rows first (`EvictOldestNonCritical`, never touching `CRITICAL` priority): `queue.max_rows` caps the table directly (`RunMaxRowsSweeper`, "keep at most N rows, overwrite the oldest once full"); `queue.storage_full_percent` is a separate disk-wide safety net (`RunStoragePressureSweeper`) for pressure from anything else sharing the volume.
- **Forwarder** (`internal/forwarder`) — ticks on `forwarder.poll_interval_ms` and dispatches batches through an `Adapter` interface — `MQTTAdapter` in production (QoS 1 + application-level ack over a dedicated ack topic), `HTTPAdapter` for dev/test. Acquisition and forwarding never block each other (Rule 1) — a dead broker just grows the local queue.
- **Deployment target**: native/systemd (not Docker — needed for `/dev/rtc0` and real `nmcli`). `deploy/nxiiot-gateway.service` (`Restart=always`) is the reference unit.

- **RTU polling-interval tuning** — the original deployment's sensor held `GOOD` down to 250ms (20x a 5000ms default) but timed out completely below that — polling limits are hardware-dependent, step down gradually on new hardware.
- **RTC hardware confirmed working on real silicon** (original deployment) — `GET /api/time` confirmed the full chain works end-to-end (`internal/time/rtc_linux.go`'s ioctls reading a real chip), not just the OS level.
- **Split Device into Connection + Device** — fixes a real shared-RTU-port corruption bug: the old flat `device` schema meant each device opened its own independent serial handle, so two devices sharing a bus corrupted each other's Modbus frames on the wire. New `connection` table holds the physical link; `device` shrank to `{name, connection_id, slave_id, polling_interval_ms, enabled}`. `modbus.Client` gained `SetUnitID(id byte)`; acquisition restructured to one goroutine per **connection**. New `/api/connections` REST resource mirrors `/api/devices`; config export/import gained a top-level `connections` array (restored before devices, matched/repointed by id — breaking change to the exported JSON shape versus the original schema). Migration auto-migrates each existing device to its own 1:1 connection (does **not** auto-consolidate — an explicit human step). Also fixed a real latent bug: SQLite's `DROP TABLE` on an FK parent with `ON DELETE CASCADE` children silently cascades under `foreign_keys=ON` even mid-migration-transaction (`PRAGMA foreign_keys=OFF` inside a `.sql` file is a documented no-op inside a transaction) — `internal/storage/storage.go`'s `migrate()` now explicitly toggles the pragma OFF/ON around each migration file and verifies `PRAGMA foreign_key_check` after.
- **Redesigned Modbus polling: continuous round-robin scan with block reads** — replaced the per-device/per-datapoint `polling_interval_ms` two-level gating scheme (a documented footgun — changing only one had no visible effect on read cadence) with a single connection-level `next_device_delay_ms` and a continuous round-robin loop. `internal/acquisition/blockplan.go` groups same-function-code datapoints by contiguous/near-adjacent register ranges (capped at the 125-register PDU limit, never splitting a datapoint's own span, tolerating small gaps up to 8 registers); FC1/FC2 (coils/discrete inputs) intentionally left ungrouped — see Todo. Migration adds `connection.next_device_delay_ms` (default 250ms, matching the known-safe floor on the original deployment's real hardware) and drops `polling_interval_ms` from both `device` and `datapoint`.
- **Devices API reports block-read count per device** — how many physical Modbus requests it takes to cover every tag each poll cycle, alongside the existing datapoint count and poll duration.
- **NTP Server field validated** (`internal/api/settings.go`'s `normalizeNTPServer`) — strips a leading `server `/`pool ` token (case-insensitive) and trims whitespace, then rejects anything still containing embedded whitespace with a `400` instead of silently saving an unresolvable value. Found because a value pasted in `/etc/ntp.conf` syntax (`server <host>`) saved successfully with no error, then failed DNS resolution at sync time and silently fell back to RTC quality.
- **MQTT ack-topic re-subscribe retry** (`internal/forwarder/mqttadapter.go`'s `onConnect`) — 3 attempts, linear backoff, then wait for next reconnect. Closes a real gap where a lost race on reconnect could leave the ack subscription missing with no retry, silently stalling Store & Forward.
- **MQTT reconnect watchdog** (`MQTTAdapter.RunReconnectWatchdog`) — forces a manual reconnect once the client has been stuck disconnected past a configurable threshold (default 45s, several multiples of paho's own 5s retry interval). Fixed a real incident where paho's own `AutoReconnect` silently stalled after a `"pingresp not received"` disconnect for 7+ minutes with the broker fully reachable. A later bug in the watchdog itself (unconditionally tearing down paho's own legitimate in-flight reconnect attempt) was found and fixed too — see HANDOFF.md bug #6.
- **`SetMaxOpenConns` raised from 1 to 4** — the real cause of a poll-duration bottleneck previously misdiagnosed as SD-card/backlog I/O contention: forcing every DB operation through one serialized connection blocked the acquisition goroutine's inserts behind slow API reads, even with WAL mode already active. A small `cycleYieldDelay` (20ms, once per full round-robin pass) was kept as defense-in-depth on top of the connection-pool fix. Raising the pool exposed a second, more serious regression — `SQLITE_BUSY_SNAPSHOT` on the forwarder's SELECT-then-UPDATE pattern — fixed with `_txlock=immediate` on the DSN. See HANDOFF.md bugs #7-8 for the full incident.

**Live-tested `max_rows` under real load the same day, found and fixed a real tuning gap** (2026-09-09) — the user re-enabled Store & Forward shortly after the above (unprompted, their own call), which let this get tested for real rather than staying theoretical:
1. Temporarily set `queue.max_rows` to 12,000 via the Settings page/API to force an eviction quickly instead of waiting the ~11 hours real growth would otherwise take. Confirmed via `journalctl` on the real device: `level=WARN msg="queue over max_rows: evicted oldest non-critical rows" total_rows=12031 max_rows=12000 evicted=100` — the sweeper fires correctly under real production write load, not just in unit tests.
2. **But found a genuine tuning gap**: `total_rows` kept climbing anyway (11598→12122 across a few seconds) even with eviction firing on schedule. Real insert rate on this device measured at **~12.5 rows/sec**, while eviction capacity was only `evict_batch_size (100) / max_rows_sweep_interval_seconds (60s)` ≈ **1.67 rows/sec** — eviction was correct but ~7x too slow to actually bound the queue at any cap, including the real 500,000 default (would just grow past it ~13% slower forever, never stabilizing). Same root-cause shape as the 2026-09-07 incident: a threshold tuned fine in isolation, never revisited against a change in real throughput.
3. **Fixed**: `queue.evict_batch_size` is no longer file-only — added to `settingsDTO.Queue` (`internal/api/settings.go`) and the Config page's Store & Forward card (`web/src/pages/ConfigPage.tsx`, "Eviction Batch Size" field with a note on why it must exceed the real write rate) so it can be tuned without an SSH config edit.
4. **Also added, so this mismatch is visible before it bites rather than only discoverable by a live test**: a live queue-write-rate metric. `internal/queue/queue.go`'s `Repository.CountInsertedSince` counts rows by `event_timestamp` in a trailing window; `internal/api/storeforward.go`'s `queueWriteRatePerSec` (30s window) computes rows/sec from it and is shared by both `GET /api/store-forward/status` (`write_rate_per_sec`, shown on Dashboard as a new "Queue Write Rate" card next to "Queue Size") and `GET /api/diagnostics` (same field, shown on the Diagnostics page as a new card) — operators can now see write rate next to the queue-size cap directly, instead of having to infer a mismatch from the queue silently growing.

**Dashboard: added an "Est. Time Until Eviction" estimate** (2026-09-09, frontend-only, no backend change) — requested directly: given a server outage, how long until old data risks being overwritten. `web/src/pages/Dashboard.tsx`'s `timeUntilEvictionSeconds` computes `(max_rows - total_rows) / write_rate_per_sec` from the three fields the Dashboard already fetches (no new API field needed) and `fmtDuration` renders it as `s`/`m`/`h`/`d`. **Incident (2026-09-10): the `max_rows`/write-rate work from the day before caused a real production incident on the live device — found live, fixed, deployed, verified. Full writeup in MEMORY.md; summary here is the resolved state.** User reported "Queue Size" stuck at 730,396/500,000, not draining. Investigation found two self-inflicted bugs, both from 2026-09-09's work:
1. `CountInsertedSince` (the `write_rate_per_sec` query) had no supporting index on `event_timestamp`, so every Dashboard/Diagnostics poll (3-5s cadence) did a full table scan over a 730k-row table — pinned CPU at 87%, degraded Modbus poll cycles to 18+ seconds (normal: <200ms), and starved the eviction sweeper itself. Fixed with `migrations/0006_data_queue_event_timestamp_index.sql`.
2. `RunMaxRowsSweeper` evicted a flat `evict_batch_size` per tick regardless of overshoot size, so once significantly over cap the queue found a new equilibrium above `max_rows` instead of ever draining to it. Fixed by scaling eviction to `min(max(evictBatchSize, overshoot), evictBatchSize*10)` (`internal/queue/maxrows.go`).
3. **Deploying fix #1 exposed a third bug**: the first correctly-scaled eviction deleted 50,000 rows in one `DELETE`, and `EvictOldestNonCritical`'s own query (`ORDER BY CASE priority ..., event_timestamp`) *also* had no supporting index — a full-table sort at that scale produced fresh `SQLITE_BUSY` failures (`failed to persist reading`, real data loss — no retry on that path). Fixed by restructuring into up to 3 per-priority-tier `DELETE`s (`internal/queue/storagepolicy.go`) backed by a new `(priority, event_timestamp)` index (`migrations/0007`).

**Verified live after the final deploy**: monitored `cpu_percent`/`total_rows` every 20s for ~3.3 minutes straight after restart. `total_rows` held in a 496k-501k band around the 500,000 cap the entire time (the intended self-correcting behavior, working for the first time). Zero `SQLITE_BUSY`/error log lines in that window. Modbus poll durations stayed healthy (49-264ms) throughout, including during two transient CPU spikes (71-75%, correlated with eviction ticks) — spikes were real but did not compound or cause any functional degradation, unlike the pre-fix pattern (sustained 87%, climbing, with actual failures). Considered resolved; the periodic CPU spikes at the cap boundary are a minor residual characteristic worth knowing about but not currently causing harm.

New regression tests: `TestRunMaxRowsSweeperScalesEvictionToOvershoot`, `TestRunMaxRowsSweeperCapsEvictionPerTick` (`internal/queue/maxrows_test.go`); `TestEvictOldestNonCriticalNeverTouchesCritical`/`TestEvictOldestNonCriticalPrefersLowestPriorityThenOldest` (pre-existing) re-verified against the restructured per-tier implementation. `go build/vet/test ./...` all pass.

**Fixed "Est. Time Until Eviction" giving a false-alarm number once `max_rows` started working correctly (2026-09-10, frontend-only)** — user noticed the Dashboard showing `57s` while the server was connected and healthy, and asked whether the math was wrong. The arithmetic was right; the formula was answering the wrong question. `(max_rows - total_rows) / write_rate_per_sec` measures time until the *next eviction tick*, not time until real data loss — and now that `RunMaxRowsSweeper` correctly keeps `total_rows` hovering right at `max_rows` (the whole point of the 2026-09-10 fix above), that gap is small essentially all the time, even though every row currently being evicted is already-`SENT` and safe to lose. Replaced with `(max_rows - pending_records - sending_records) / write_rate_per_sec` in `web/src/pages/Dashboard.tsx`'s `timeUntilEvictionSeconds` — doesn't depend on `total_rows`/how much `SENT` buffer exists at all, because eviction consumes that buffer first regardless of its size: the real budget is just "how many more undelivered rows can accumulate before `max_rows` is reached with no `SENT` buffer left to sacrifice," which reduces to `max_rows` minus *currently* undelivered rows. Sanity check against real numbers: `pending_records` was ~15 in the same window that showed `57s` — new formula gives ~5.9 hours instead, which matches reality (server was connected and healthy, not seconds from data loss). Card renamed "Est. Time Until Data Loss Risk" to better match what it now measures. Caveat kept in the code comment: eviction order is priority-tier first, so if `PENDING` data happens to sit in a lower-priority tier than old `SENT` data, real risk could arrive somewhat sooner than this estimate — still far more accurate than the previous formula. Verified: `npm run build` passes with no type errors. Not yet deployed (frontend-only, no binary/migration change — same low-risk `web-dist` swap with no restart as the 2026-09-09 deploy).

**Incident (2026-09-11): `/userdata` hit 100% on the live device; recovered without data-file deletion or a reinstall.** Established facts: the 1.6 GB ext4 partition `/userdata` (which held only the gateway) had 0 bytes available; `gateway.db` was 638 MB and `gateway.db-wal` was 870 MB (924,672,232 B when measured — larger than the DB itself); every reading failed with `failed to persist reading ... database or disk is full (13)` (real data loss) and the storage-full sweeper failed with the same error each 60s tick, so the app could not heal itself. Device config had `queue.max_rows: 2500000` (repo default is 500,000) with ~1.98M rows in the queue. **Inferred, not proven:** a 2.5M-row cap on a 1.6 GB partition leaves no room for WAL growth, and once free space is 0 the sweeper's own `DELETE` cannot run. Why the WAL reached 870 MB was not root-caused.
- Deleting 13 stale deploy artifacts (`gateway.bak-*`, `gateway.new`, `web-dist.old-*/.bak-*/.new`, ~79 MB) did **not** change `df` Available (still 0): ext4 reserves 5% (21,542 × 4 KiB ≈ 84 MB) for root, though root can still write there (a 10 MB `dd` succeeded). The gateway kept logging disk-full afterwards; why was not determined.
- `tune2fs -m 1 /dev/mmcblk0p10` fails with `Filesystem has unsupported read-only feature(s)` — `dumpe2fs -h` shows non-standard flags (`FEATURE_C12`, `FEATURE_R16`) on the vendor image; e2fsprogs on the device is 1.45.5. Do not force it.
- **What worked**: stopped the service, then ran a one-off `PRAGMA wal_checkpoint(TRUNCATE)` against the stopped DB (no `sqlite3` CLI on the device, so a tiny Go program using the repo's own `modernc.org/sqlite`, cross-compiled `GOOS=linux GOARCH=arm GOARM=7 CGO_ENABLED=0`, run from `/tmp`, removed afterwards). WAL 924,672,232 → 0 B, DB file size unchanged (668,803,072 B), `/userdata` 100% → 44% used, 863 MB available. ## Todo / Out of scope

- **FC1/FC2 (coil/discrete input) decoding is broken independent of anything recent** — `DataType.RegisterCount()`'s byte-width math doesn't match Modbus's bit-packed coil/discrete-input response format. Not currently blocking anything unless a coil/discrete-input datapoint is configured, but will bite the first time one is.
- **`datapoint.word_order` is a dead field** — persisted since the first migration, never used by decode logic, never exposed in any UI. `byte_order` alone already fully specifies both byte and word order for 32/64-bit types via its permutation string (ABCD/BADC/CDAB/DCBA, plus Natural/Reversed for 64-bit). Two ways to close this, not decided: wire it up as a real independent second axis, or remove the dead column entirely.
- **`modbus.ReadWithRetry` is called with `maxRetries=0` hardcoded** even though `connection.Connection.Retry` exists, is validated, and is otherwise unused.
- **`gateway.db` doesn't shrink on disk after a retention sweep deletes rows** — SQLite frees pages internally for reuse, doesn't return them to the OS without `VACUUM` or `auto_vacuum`. Needs an exclusive lock on the whole file for its duration — time it against real traffic before running on a live device.
- **`netconfig.ApplyStatic`/confirm-revert flow**: `Current()` is verified live; the actual apply-and-auto-revert-on-timeout path is deliberately deferred until physical console access is arranged (a bad apply could lock out the only remote path to the device).
- **RTU failure paths**: unplug-mid-poll (`DEVICE_OFFLINE`) and forced-bad-response (`CRC_ERROR`) haven't been triggered from live hardware yet on the original deployment.
- **RTC DKMS auto-rebuild is inferred, not proven against a real kernel upgrade** — if this device uses a similar out-of-tree RTC driver, verify `/dev/rtc0` and `dmesg | grep -i rtc` after any kernel upgrade rather than assuming it survives.
- **Out of scope for now**: V2/V3 roadmap items (HTTPS adapter, user management, alarm management, fleet management, OTA updates). Nothing currently blocks starting any of them; just not prioritized yet.

**Root cause found for a real "Clock Offset: 3053.9ms" report on the live device's Time page, and fixed (2026-09-04, same day)** — investigated live rather than guessing: `timedatectl status` on the device showed `System clock synchronized: no` / `NTP service: inactive` (no `chronyd`/`systemd-timesyncd`/`ntpd` running at all), directly contradicting the gateway's own `time_quality: "SYNCED"`.    - `log.level: info → warn` (was producing ~19-30 log lines/sec across the 4 connections, enough overhead to starve the API server of CPU on the device's 3 cores)
   - `next_device_delay_ms: 250 → 500` on all 4 connections (250ms is still the correct *per-connection* floor from the original hardware tuning; nothing coordinates load *across* connections, so 4 of them needed a wider gap each)
   - `queue.retention_days: 3 → 1` (at the real insert rate, 3 days had grown to ~4.9M rows / 1.3GB — keeps future steady-state size proportional to what this SD card can sustain)
   - **One-time offline cleanup**: stopped the service, deleted all 4,918,075 `SENT` rows in checkpointed 200k-row batches (kept the 407 live `PENDING`/`SENDING` rows), then `VACUUM`ed — `gateway.db`: 1.19GB → 19MB, `/userdata`: 89% → 2% used. Also vacuumed 466MB of journald logs (mostly this incident's own log flood) down to 32MB and capped `journald.conf`'s `SystemMaxUse=200M` against a repeat.

**Result:** CPU dropped from a sustained 165-233% (over 2 full cores on a 3-core box) to 2.5%. Every API endpoint responds in single-digit milliseconds now. Modbus/RTU hardware itself never showed a single timeout or CRC error through the whole incident — confirms this was purely an application/storage-layer problem, never a hardware one.

**As of this writeup, Store & Forward is still `disabled`** (`store_forward.disabled: true`, flipped mid-investigation as a mitigation) — 9 `PENDING` + 398 `SENDING` rows are waiting. Re-enabling it (and confirming the fixes above hold under real write load again) is the next step for whoever picks this up.

## Data Contracts

Interfaces this gateway depends on — flag before changing either of these, since any downstream MQTT consumer depends on them matching exactly.

- **MQTT data topic** (gateway → broker): `gateway/{gateway_id}/data`, QoS 1, JSON:
  `{ "batch_id": string, "entries": [{ "gateway_id": string, "sequence_id": int64, "device_id": int64, "datapoint_id": int64, "value": float64|null, "quality": "GOOD"|"CRC_ERROR"|"DEVICE_OFFLINE"|"INVALID"|"TIMEOUT", "event_timestamp": RFC3339, "priority": string }] }`
  (`internal/forwarder/wire.go`'s `WireEntry`.)
- **MQTT ack topic** (consumer → gateway): `gateway/{gateway_id}/ack`, QoS 1, JSON: `{ "batch_id": string, "error": string (optional) }`. Any consumer must derive this from the data topic it received (`strings.TrimSuffix(topic, "/data") + "/ack"`), not hardcode a gateway ID.
- **Gateway REST API**: connections (`GET/POST/PUT/DELETE /api/connections`), devices (`GET/POST/PUT/DELETE /api/devices`), and datapoints (`GET/POST/PUT/DELETE /api/datapoints`). A device carries only `connection_id`/`slave_id`/`polling_interval_ms`/`enabled` — protocol/interface/baud/etc live on the connection it references. `DELETE /api/connections/{id}` returns `409` while any device still references it. Config export/import (`GET/POST /api/config/export|import`) carries a top-level `connections` array restored before `devices`.
