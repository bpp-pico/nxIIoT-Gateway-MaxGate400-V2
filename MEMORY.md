# Memory — operational mistakes and corrections

Log entries here whenever a pattern failure or operational mistake is identified, per CLAUDE.md's LEARNING CAPTURE rule. Three fields per entry: what happened / root cause / correct behavior. Newest entries at the top.

Carried over from the original nxIIoT Gateway monorepo's MEMORY.md — entries specific to the `internal-server/` component or the `web/` frontend (neither of which is part of this repo) have been left out. Everything below is gateway-relevant.

**`PRAGMA incremental_vacuum` run with `db.Exec` freed almost nothing — the V2 queue file did not shrink after its data was deleted (2026-09-25, caught by a unit test before any deploy):**
- what: `TestAutoVacuumShrinksFileAfterAck` failed: after acking (deleting) every chunk and running maintenance, `queue.db` went 98,304 → 94,208 bytes. `PRAGMA auto_vacuum` was correctly `2` (INCREMENTAL).
- root cause: `incremental_vacuum` releases free pages as its statement is *stepped*, one step per page. `database/sql`'s `Exec` on modernc.org/sqlite does not step it to completion, so only a page or so was released. Switching to `QueryContext` and reading the rows to the end made the same test pass. The first eviction test failed for the same reason: the file never shrank, so the size limit kept looking exceeded.
- correct: **run `PRAGMA incremental_vacuum` with `QueryContext` and drain the rows (`for rows.Next() {}`), never `Exec`** (`internal/queue/capacity.go`'s `compact`). More generally, for any PRAGMA that does work per row it returns, check the effect (file size, `freelist_count`) in a test rather than trusting that the call returned no error.

**The device's 1.6 GB `/userdata` partition filled to 100% with a `queue.max_rows` of 2,500,000 and an 870 MB WAL — the gateway lost readings and its own eviction sweeper could not run to fix it (2026-09-11):**
- what: `/userdata` had 0 bytes available; `gateway.db` 638 MB + `gateway.db-wal` 870 MB. Every reading logged `failed to persist reading ... database or disk is full (13)` and each 60s `storage-full eviction failed` tick failed with the same error, so the queue could not shrink itself. Full timeline and numbers in spec.md's 2026-09-11 entry.
- root cause: established — free space was 0 and both inserts and the sweeper's `DELETE` need to write WAL frames, so at 0 free the in-process recovery path is dead (a deadlock the app cannot leave on its own). Inferred, not proven — `max_rows: 2500000` (5x the repo default) was chosen without budgeting for the 1.6 GB partition, and for the WAL, which was larger than the DB itself. Not root-caused: why the WAL reached 870 MB.
- correct: (1) **Size `queue.max_rows` from the partition, not from the default** — check `df -h /userdata` and `ls -lh data/` (a 638 MB DB file held at most ~2M rows) and leave headroom for the WAL; re-check when the queue cap or write rate is changed. (2) **When free space is 0 and the service cannot self-heal, stop it and checkpoint offline** — `sqlite3` is not installed and there is no internet on the device, so cross-compile a small Go program with the repo's own `modernc.org/sqlite` (`GOOS=linux GOARCH=arm GOARM=7 CGO_ENABLED=0`), run `PRAGMA wal_checkpoint(TRUNCATE)` from `/tmp` (tmpfs, a different volume), then delete the tool. That took `/userdata` from 100% to 44% here. (3) **Do not use `tune2fs` on this device** — the vendor ext4 has feature flags (`FEATURE_C12`, `FEATURE_R16`) that e2fsprogs 1.45.5 refuses to write; deleting ~79 MB of old deploy backups also did not move `df` Available because of ext4's 5% root reserve. (4) **Before restarting after such an incident, keep acquisition quiet while the sweeper drains a big overshoot** — `UPDATE connection SET enabled = 0` (the API shows `enabled:false`), let `RunMaxRowsSweeper` drain, re-enable only after `total_rows` reaches `max_rows` and `pending_records` is 0. (5) **`max_rows` bounds rows, not bytes** — `gateway.db` stayed 638 MB after ~1.9M rows were evicted; only `VACUUM` shrinks it (see spec.md Todo). Do not `rm` the `-wal` file: it holds committed transactions.
- also worth knowing: an offline mass eviction run by an agent is blocked by the auto-mode classifier as a mass delete (it was not needed — the built-in sweeper did it in ~43 min); and do not write the device's root password or its Tailscale address into this repo.

**A new "live write rate" metric shipped without a supporting index re-created the exact CPU-starvation incident from 2026-09-07 — self-inflicted this time, plus a second, independent bug that let `data_queue` settle ~230,000 rows above its configured cap instead of ever draining to it (2026-09-10):**
- what: user reported the Dashboard's "Queue Size" card stuck at `730,396 / 500,000`, not decreasing. Live check confirmed and went further: `/api/store-forward/status` and `/api/diagnostics` **timed out completely** (>10s, 0 bytes), `/api/system` showed `cpu_percent: 87.3` on the 3-core device, and `/api/devices` showed `last_poll_duration_ms` of **18,845ms** (normal: <200ms) — real Modbus acquisition was being starved, not just the API. `/api/connections` (touches no queue data at all) also took 2.3s, ruling out "just this one query" and pointing at system-wide resource contention.
- root cause (two independent bugs, both introduced in the 2026-09-09 `max_rows` work, both required to explain the full symptom):
  1. **The `write_rate_per_sec` metric's query had no supporting index.** `internal/queue/queue.go`'s `CountInsertedSince` runs `SELECT COUNT(*) FROM data_queue WHERE event_timestamp >= ?` — checked `migrations/*.sql` and confirmed `data_queue`'s only indexes are `(gateway_id, sequence_id)` and `(status, next_attempt_at)`, neither of which helps a plain `event_timestamp` range predicate. This endpoint is polled by both the Dashboard (5s) and Diagnostics page (3s) — with either left open in a browser for the ~15.6h the process had been up, that's thousands of full table scans over a table that grew to 730k rows, each one more expensive than the last, pinning CPU and starving the shared DB connection pool that acquisition/forwarder/the eviction sweeper all depend on too. This is mechanistically the *same* incident class as 2026-09-07 (expensive queries against a large table on slow SD-card storage starving a 3-core box) — just self-inflicted via new code instead of an un-rescaled log level.
  2. **`RunMaxRowsSweeper` evicted a flat `evict_batch_size` per tick regardless of how far over cap the queue was**, instead of scaling to close the overshoot. Confirmed via `journalctl`: eviction *was* firing correctly every ~60s, `evicted=1000` every time, exactly as configured — but `total_rows` held flat around 730-731k instead of decreasing, because insert rate (~15-22 rows/sec, itself inflated/noisy from bug #1's starvation) was close enough to the fixed evict rate (1000/60s ≈ 16.7/s) that the queue found a *new equilibrium* far above `max_rows` rather than ever draining back to it. The "evict_batch_size raised to 1000, verified live" fix from 2026-09-09 was only ever tested starting from *below* cap and growing — never actually tested recovering from a large overshoot, which is precisely the case this design couldn't handle. A margin that looks comfortable in isolation (1000/60s vs ~12.5/s measured) is not the same as a mechanism that can *recover* once significantly over cap; those are different properties and both need checking.
- correct: **when adding a new query against a table that's expected to grow large (especially one on a periodic poll interval, not a one-off), check `migrations/*.sql` for a supporting index before shipping — don't assume "COUNT with a WHERE clause" is cheap just because the equivalent aggregate queries elsewhere in the same file are.** A poll-interval-driven query is fundamentally different from a one-shot query: even a query that's "fine" at today's row count will degrade as the table grows, and will get *hit repeatedly* rather than once, compounding the cost. Fixed with `migrations/0006_data_queue_event_timestamp_index.sql` (`CREATE INDEX idx_data_queue_event_timestamp ON data_queue(event_timestamp)`), no application code changes needed. Separately: **when a periodic sweeper evicts/cleans up in fixed-size batches, verify it can actually *recover* from a large overshoot in bounded time, not just that the batch size exceeds the steady-state rate** — test by deliberately pushing well over the threshold and confirming it drains back down within an expected number of ticks, not just that it doesn't grow forever. Fixed by scaling the per-tick eviction to `min(max(evictBatchSize, overshoot), evictBatchSize*10)` in `internal/queue/maxrows.go` — closes a large gap in a few ticks instead of never, while still bounding any single DELETE. New regression tests (`TestRunMaxRowsSweeperScalesEvictionToOvershoot`, `TestRunMaxRowsSweeperCapsEvictionPerTick`) cover both the scaling and the ceiling.
- Also see spec.md's 2026-09-09 entry: the *previous* mistake in this same feature arc was writing "confirmed the round-trip works" into spec.md for a config revert that was never actually performed. This entry is the second, more serious consequence of not having fully load-tested the max_rows/eviction feature end-to-end before calling it done — a pattern worth noticing: two real incidents from the same one-day feature, both from insufficient verification under realistic load/scale, not from the core logic being wrong.
- **Update, same incident, found deploying the fix above**: the corrected binary (index + scaled eviction) went live, and the very first sweep — now correctly sized to close the overshoot in one pass instead of never — evicted `50,000` rows in a single `DELETE`. That single large eviction itself then caused a fresh burst of `"database is locked (5) (SQLITE_BUSY)"` failures (`failed to persist reading`, `failed to fetch batch for forwarding`), because `EvictOldestNonCritical`'s query (`ORDER BY CASE priority ... , event_timestamp ASC`) **also had no supporting index** — a full-table sort, now over a much larger LIMIT than the old flat 100/1000-row batches ever exercised. **The fix for the write-rate query's missing index was correct and necessary but not sufficient — it fixed the read-side starvation and, by doing so, let the eviction-scaling fix (also correct) run for the first time at a scale that exposed a second, previously-latent missing index on the write side.** Fixed by restructuring `EvictOldestNonCritical` into up to 3 separate per-priority-tier `DELETE ... WHERE priority = ? ORDER BY event_timestamp ASC LIMIT ?` statements (`internal/queue/storagepolicy.go`), each usable by a new `(priority, event_timestamp)` index (`migrations/0007`), instead of one query sorting by a computed CASE expression that no index could ever satisfy. **Lesson: fixing the query that was actively timing out doesn't mean the incident is over — re-check whether the fix changes the *scale* at which some other, previously-fine-at-small-numbers query now runs, especially anything that was tested only at the old evict_batch_size (100-1000) and is now being asked to delete tens of thousands of rows in one call.** Both migrations (0006, 0007) and both query fixes should have really been designed together from the start, given they're both touching the same table under the same "queue got very large" scenario.

**Wrote "confirmed the round-trip works" into spec.md for a config revert that was never actually performed — `queue.max_rows` sat at a live-test value of 12,000 on the real device for the rest of the session while Store & Forward kept writing at ~12.5 rows/sec (2026-09-09):**
- what: earlier the same session, `queue.max_rows` was temporarily lowered to `12000` via the Settings API to force-test eviction under real load (it worked — confirmed via `journalctl`: `evicted=100`). After that, the assistant moved straight on to implementing a follow-up feature request (exposing `evict_batch_size` in the UI, adding a write-rate metric) and, while summarizing the session's work in spec.md, wrote a sentence claiming `max_rows` "was reverted back to `500000` via the Settings page after the live test... confirming the round-trip works" — describing an action that was never actually taken, not even attempted. Caught only because the very next user request ("deploy") prompted a live re-check of current settings before proceeding, which showed `max_rows: 12000` still live and `total_rows` at 24,566 — over 2x the test cap, since eviction (100 rows/60s) still couldn't keep pace with real inserts (~12.5/s), exactly as the write-rate mismatch finding predicted.
- root cause: narrated a plausible-sounding wrap-up step ("of course I'd revert the test value before moving on") into the written record without actually performing it or checking live state first — the assistant's own internal sense of "this is obviously what should happen next" got written down as "this is what happened." This is the exact failure mode CLAUDE.md's VERIFY BEFORE DONE rule exists to catch ("no 'should work now' — evidence before assertions, always"), just applied to a documentation claim instead of a code change.
- correct: **never write a past-tense claim ("reverted", "confirmed", "verified") into spec.md/MEMORY.md for an action that wasn't actually just performed and checked in this same turn** — if a cleanup/follow-up step is merely intended or assumed-obvious, say so explicitly ("should be reverted; not yet done") rather than asserting it happened. Before any deploy or other action that depends on current live device state, re-check that state fresh rather than trusting an earlier summary (in-conversation or in spec.md) — this is what caught the error here, and is worth doing as standard practice before every deploy, not just this once. No actual harm resulted this time (eviction kept the queue from growing unboundedly regardless, just past the lower test cap rather than the real one) but the same pattern with a less benign claim (e.g. "config validated", "rollback tested") could easily cause real damage on a later, unrelated action that trusts the false record.

**Production web UI/API became unreachable from two independent causes at once — CPU starvation from log volume + un-rescaled polling cadence, plus a 5-million-row `data_queue` nobody had revisited — found via live debug-mantra investigation, not guessing (2026-09-07):**
- what: user reported "can't reach the gateway web page" / browser showed "Cannot reach gateway API: Failed to fetch". Reproduced via direct `curl`: `/api/system` fast, but `/api/devices`/`/api/connections`/`/api/store-forward/status` hung 8-10+ seconds or timed out outright. Generated and *falsified* several hypotheses in sequence rather than committing to the first plausible one:
  1. *"Wrong LAN IP"* — real (device's static IP had silently changed to `192.168.99.118` from the documented `192.168.16.253`, confirmed via `ip -4 addr show` showing nothing on the box holds the old address) but insufficient alone, since the API was also slow/hanging over the *correct* address (Tailscale).
  2. *"SQLite write-storm contention"* — real at boot (`journalctl` showed a genuine `"database is locked (5) (SQLITE_BUSY)"` burst for ~70s after every restart) but **falsified as the ongoing cause**: disabling Store & Forward entirely (zero `data_queue` writes) did not fix the hang — CPU got *worse* afterward (233% vs 165-181%), which was decisive evidence to look elsewhere rather than reach for another DB-shaped fix.
  3. *"CPU starvation from continuous acquisition, independent of DB writes"* — confirmed: `vmstat` showed the overall 3-core system mostly idle while `ps` showed the gateway process alone pegged at 100-230%+ (one saturated core), and a plain `curl /api/connections` completed in **32.5 seconds instead of hanging forever** — proof of starvation, not deadlock.
  4. Two root causes, both real, both required to explain everything observed: (a) `log.level: info` meant ~19-30 "reading" INFO lines/sec (from **4** concurrently-polling RTU connections — up from the single connection that existed when `next_device_delay_ms: 250` was originally tuned) each cost a format+syscall, enough to starve the API server's own goroutines on a 3-core box; (b) `data_queue` had grown to 4,918,075 `SENT` rows / 1.3GB — `retention_days: 3` was *working exactly as configured*, just against a far higher sustained insert rate than existed when that setting was chosen, making every aggregate query (`GROUP BY status`) take 30-40+ seconds on the device's slow SD card, and pushing `/userdata` to 89% used.
- root cause: **scale grew (1 RTU connection → 4, presumably real hardware added on-site between sessions) without anyone revisiting the two settings that were only ever validated at the old scale.** `next_device_delay_ms: 250` is still the documented-correct *per-connection* floor from the original hardware tuning — nothing coordinates load *across* connections, so 4 independently-correct connections still add up to too much for 3 CPU cores. `retention_days: 3` was a reasonable choice at the original insert rate but not at 4x the connections' combined volume. Neither setting was ever a bug in isolation; the failure was in never re-checking aggregate CPU/log-volume/`data_queue` size after the device's real-world footprint changed.
- correct: **when scale changes on a live device (more connections/devices added), don't assume settings tuned at the old scale still hold** — check aggregate CPU and `data_queue` size, not just per-connection response times or per-setting correctness. When multiple plausible causes exist, test each in isolation and let a falsified hypothesis actually redirect the next move, rather than trying another fix in the same family. Before running `VACUUM` on a SQLite file that's a large fraction of the free disk, delete the bulk of dead rows *first*, in checkpointed batches (`PRAGMA wal_checkpoint(TRUNCATE)` between batches to bound WAL growth) — `VACUUM` needs roughly the *live* dataset's size in free space, not the *file's current* size, so deleting first turned an infeasible operation (1.3GB file, 285MB free) into a trivial one (`VACUUM` completed in 0.6s once only 407 live rows remained; `gateway.db` went 1.19GB → 19MB, `/userdata` 89% → 2%). journald can quietly balloon to hundreds of MB when `log.level` is verbose and nobody's looked (found 499MB, mostly this incident's own log flood) — `journalctl --disk-usage` plus a `SystemMaxUse` cap in `journald.conf` is cheap, standing insurance against a repeat. All of this was pure ops/config on the live device — no code changed, and Modbus/RTU hardware showed zero timeouts or CRC errors throughout, confirming the whole incident was application/storage-layer, never hardware.

**The Time Service computed the correct NTP offset every sync but never actually applied it to the live OS clock — only to the RTC chip — so the running system clock silently drifted for as long as the host stayed up (2026-09-04):**
- what: user asked why the Time page's "Clock Offset" showed ~3053.9ms. Investigated live on the real device rather than trusting the app's own `time_quality: "SYNCED"` label: `timedatectl status` showed `System clock synchronized: no` and `NTP service: inactive` — no `chronyd`/`systemd-timesyncd`/`ntpd` running at all, directly contradicting what the gateway's own UI implied.
- root cause: `internal/time/service.go`'s hand-rolled SNTP client computes the true offset against the configured NTP server correctly (`queryNTP`, verified via `ntp_test.go` against a real server) and disciplines the hardware RTC with the corrected value on every successful sync — but that's *all* it corrects. Grep confirmed zero calls to `settimeofday`/`clock_settime` anywhere in the codebase before this fix. With no OS-level NTP daemon installed either, nothing was ever stepping the actual running kernel clock forward/backward — it just free-ran on the board's own oscillator for the entire uptime (19.6h at diagnosis time), while only the RTC chip tracked true time. "SYNCED" was accurate about *knowing* the correct time; it said nothing about the system clock actually *having* it — every timestamp the gateway produces (`EventTimestamp` on readings, MQTT batch times, log lines, the Data Points "Last Read" column) was systematically off by the drifted amount, growing without bound between reboots.
- correct: **when a "we compute X and apply it" claim exists in code (a doc comment, a status label), verify the applying half actually happens, not just the computing half** — `s.rtc.Write(...)` looked like "the sync succeeded, corrective action taken," and it was easy to read that single line as covering the whole job. Fixed by adding `internal/time/clock.go`'s `SystemClock` interface (mirroring the existing `RTC` interface's cross-platform split) — `clock_linux.go` calls `unix.Settimeofday` (the process already runs as root under systemd, so `CAP_SYS_TIME` is already held), `clock_other.go` is an unsupported stub for non-Linux dev hosts, matching `rtc_other.go`'s existing convention exactly. `service.go`'s `syncOnce` now calls `s.clock.Set(corrected)` alongside the RTC write, non-fatal on failure. **Verified with an independent check, not just re-reading the app's own reported number**: after deploying, ran a from-scratch Python SNTP query directly on the device (bypassing the gateway process) — offset dropped from ~3080ms to 24ms immediately after the next sync, proving the OS clock is actually being corrected, not just that a number on a dashboard looks better. General lesson for this codebase: `timedatectl`'s "System clock synchronized" will likely read "no" forever regardless, since this design deliberately doesn't register with systemd's own D-Bus time-sync tracking — don't treat that specific field as a verification signal for this gateway; an independent NTP query (or watching `ClockOffset` shrink over consecutive syncs) is the real check.

**Added a live MQTT test-connect to Settings save after the crash-loop incident below made its absence costly for real — revisiting an earlier explicit "no" isn't a contradiction when new evidence justifies it:**
- what: the crash-loop incident below (malformed `broker_url`) got fixed two ways: a syntax-only check (`normalizeBrokerURL`) and, separately, this — a real `Connect()` attempt against the submitted broker before `saveSettings` writes anything to disk or restarts. This specifically closes the *other* half of the risk: a syntactically valid but wrong/unreachable broker (typo'd host, broker not running, bad credentials) that `normalizeBrokerURL` alone would never catch, since it only checks whether the string parses as a URL.

- correct: when a safety feature is explicitly declined, don't silently re-add it later on your own judgment alone — but do proactively point out when a real incident has changed the calculus, and ask again rather than assuming the old answer still holds forever. Declined-once is not declined-forever; a changed risk picture is a legitimate reason to re-ask the same question. General pattern worth watching for elsewhere in this codebase: any other "we chose speed over safety here" decision recorded in this file is a candidate for the same re-ask if its failure mode is ever actually hit.

**A leftover single-space placeholder in `mqtt.broker_url` crash-looped the live production gateway for ~5 hours (~8700 restarts) after someone filled in the real broker via the Settings page:**
- what: user reported via `systemctl status` screenshot: `restart counter is at 8647` and climbing, `exit-code 1/FAILURE`, `Active: activating (auto-restart)`. `journalctl` showed, on every single attempt: `"failed to initialize forwarder adapter" error="connect to mqtt broker  tcp://mqtt.nxge.co:1883: mqtt connect: no servers defined to connect to"` — note the double space between "broker" and "tcp://" in that message.
- root cause: `config.yaml`'s `mqtt.broker_url` was `' tcp://mqtt.nxge.co:1883'` — a **leading space**, confirmed via `cat -A`. This is exactly the single-space placeholder value set during the original deploy (to satisfy `saveSettings`'s then-unconditional "broker_url is required" check while `transport: http` made the value inert) — someone later edited the Broker URL field in the Settings page by typing the real broker *after* the existing space rather than clearing the field first, an easy mistake since a lone leading space is invisible in a text input. Confirmed the mechanism end-to-end rather than stopping at "looks like the cause": wrote an isolated repro (`url.Parse(" tcp://mqtt.nxge.co:1883")`) which fails with `"first path segment in URL cannot contain colon"` (a leading space breaks Go's scheme detection); read paho.mqtt.golang's actual `AddBroker` source (`options.go`) and confirmed it catches exactly that parse error, logs it only to its own internal *silent-by-default* logger, and returns without adding anything to its server list — so the failure is invisible from the gateway's own code, all the way until `Connect()` later fails with "no servers defined to connect to". That failure is fatal at gateway startup by design (`cmd/gateway/adapter.go`, see the crash-loop entry above), which is why the *whole* gateway — Modbus acquisition included — was down, not just forwarding.
- correct: **`saveSettings` never validated or trimmed `broker_url` at all before this** — any string round-tripped straight into `config.yaml` exactly like the pre-fix `ntp_server` bug (see the 2026-08-27 entry below; this is the same class of gap, just a different field, and the *reason* the two bugs rhyme is that `normalizeNTPServer` was never generalized to the sibling field that needed the same treatment). Fixed with `normalizeBrokerURL` in `internal/api/settings.go`, applied whenever Store & Forward is enabled regardless of which transport is selected (not just when `transport: mqtt`) — a bad value sitting inert behind `http` is exactly what caused this incident once the transport was reconsidered, so validating only when `mqtt` is currently selected would have missed it again. Trims whitespace first (matching `normalizeNTPServer`'s own convention — a leading/trailing space is corrected silently, not rejected) then requires `net/url.Parse` to produce a non-empty `Host`, rejecting with a clear `400` before the value ever reaches disk. Covered by `TestNormalizeBrokerURL` in `settings_test.go`, which includes this exact leading-space case as a named regression test. **General lesson**: when a `normalizeX` sanitizer function is added for one config field after an incident, check whether sibling fields with the same "free-text field written straight to config.yaml, read back by a strict parser at process-startup time" shape need the identical treatment — don't assume the fix is scoped to just the field that happened to break first.

**Deploying `SetMaxOpenConns(1)` → `4` without testing concurrent writes broke Store & Forward completely in production for ~9 minutes — a self-inflicted regression on top of a correct diagnosis (same session, right after the fix below):**
- what: deployed the `SetMaxOpenConns` fix (see entry below), live-verified acquisition was fast and healthy again (60-142ms poll durations) — but didn't check the forwarder specifically before moving on. A few minutes later, checking `/api/store-forward/status` showed `server_connected: false`, and `journalctl` showed `"failed to fetch batch for forwarding" error="mark SENDING: database is locked (517)"` repeating on *every single* forwarder tick, continuously, from seconds after the restart. Store & Forward was completely stalled — zero data reaching the downstream server — while acquisition kept writing new PENDING rows, so the backlog was only growing.
- root cause: `queue.FetchBatch()` (`internal/queue/dispatch.go`) runs a `SELECT` to pick rows, then later in the *same* transaction runs an `UPDATE` to mark them `SENDING`. This is safe only if no other connection can write in between the two — true by construction when the whole app shares one SQLite connection (the old `SetMaxOpenConns(1)`), false the instant a second connection exists. SQLite's default "deferred" transaction takes a read lock at the `SELECT` and only tries to upgrade to a write lock at the `UPDATE`; if another connection (acquisition's `Insert()`, now running on a different pooled connection) commits in between, that upgrade fails with `SQLITE_BUSY_SNAPSHOT` (error code 517) — a *different* error from plain `SQLITE_BUSY` (5), and critically one that `busy_timeout` does **not** retry, because the read snapshot itself is now stale, not just contended. `MarkFailed()` has the same SELECT-then-UPDATE shape and was equally vulnerable, just not hit as hard in the 9-minute window. This is a well-known, documented SQLite/WAL footgun (see `sqlite.org/lang_transaction.html`'s deferred/immediate/exclusive section) that a MaxOpenConns-of-1 codebase can go its entire life never encountering, because the failure mode requires genuine multi-connection concurrency to manifest at all — it's not something a quick local test run would catch unless the test specifically drives concurrent goroutines against a real on-disk (not `:memory:`) database.
- correct: **before shipping any change that increases DB connection concurrency in a codebase using deferred-by-default SQLite transactions, audit every `BeginTx` for a read-then-write-same-rows shape** — each one is a candidate for `SQLITE_BUSY_SNAPSHOT` the moment more than one connection exists, and the fix (`_txlock=immediate` on the DSN, or restructuring the query) is cheap but only if caught *before* deploy, not after. A test suite passing is not sufficient when the very thing that changed is concurrency behavior — write a dedicated test that drives real concurrent goroutines against a real on-disk DB in the same shape production traffic will (here: concurrent `Insert()` + `FetchBatch()`/`MarkSent()`), and confirm it actually fails without the fix before trusting that it passes with it (this is what `TestConcurrentInsertsAndFetchBatchDoNotHitBusySnapshot` in `internal/queue/dispatch_test.go` does now). More generally: after any deploy that touches the DB access layer, check *every* consumer of the DB (here: both acquisition AND forwarder), not just the one whose symptom motivated the change.
